From a shared application state to partially observable, multi-actor transition systems

A working formalization for an AI R&D OS

Verdict. The document is a good design checklist and a weak formal theory. The six-part state decomposition, the Ereal against Ê split, the version-bound approval rule, and the caveats in §3, §11, §15, §16, and the last subsection are correct and useful. As a formal object it has 4 structural defects: St has two meanings, 3 action models conflict, the time index t is never defined, and 12 symbols carry two or more meanings. It states no result that follows from its definitions. Nothing in 𝔄 (§17) separates an agent-native application from any multi-user application with a bot.

The starting point is

St+1=F(St,at),at∈𝒜human∪𝒜agent.S_{t+1}=F(S_t,a_t), \qquad a_t\in\mathcal A_{\mathrm{human}}\cup\mathcal A_{\mathrm{agent}}.

A human and an agent can change the same underlying application state. A rigorous account extends this equation to a partially observable, multi-actor controlled dynamical system with typed state, provenance, permissions, and constrained transitions. The simple deterministic equation is a special case.

Reviewer notes · §0 · The starting equation

R1StrengthStarting from St+1 = F(St, at) and later showing it as a special case (§9, point mass) is a good structure. The reader sees what each extension adds.
R2WeaknessThe index t is never defined. It can mean wall-clock ticks, request count, or position in the event log. Human and agent actions arrive asynchronously, so one global discrete step is an assumption. §15 depends on the answer: serialization only makes sense if t counts committed actions.
R2 fixRecommendationAdd to §0, after the first equation: “Time t ∈ ℕ counts committed events. Step t is the t-th entry in the event log. Wall-clock time is an attribute of each event, not the index.” Then T in §9 is a kernel per committed event, and the serialization in §15 is the log order.
R3Weaknessat ∈ 𝒜human ∪ 𝒜agent loses the actor when the two sets overlap. “Edit document” is in both sets, so this equation cannot say who edited. §18 repairs this with it. State the repair here.
R3 fixRecommendationReplace the §0 equation with St+1 = F(St, it, at), at ∈ 𝒜it(St), it ∈ ℐ. Keep 𝒜human and 𝒜agent only as names for the union over each actor group. Every event already has an actor field (§11), so this change costs nothing in the implementation.

1. State space

Let St∈𝒮S_t\in\mathcal S be the complete state of the modeled system. Begin with a product decomposition:

𝒮=𝒳×𝒦×𝒲×ℛ×𝒫×ℰ,St=(Xt,Kt,Wt,Rt,Pt,Et).\mathcal S=\mathcal X\times\mathcal K\times\mathcal W\times\mathcal R\times\mathcal P\times\mathcal E, \qquad S_t=(X_t,K_t,W_t,R_t,P_t,E_t).

Component Meaning
XtX_t Domain and operational state
KtK_t Knowledge and epistemic state
WtW_t Workflow and process state
RtR_t Runtime state of agents
PtP_t Policies, permissions, and invariants
EtE_t External environment state

These components have different semantics even when stored in the same database.

Every Markov claim, every invariant, and the event-sourcing reconstruction depend on which meaning applies.

Concrete edits: (1) §1, first sentence: “Let Stworld be the complete state of the modeled world.” (2) Add: “Stowned = ω(Stworld), where ω keeps X, K, W, P, Ê, Π, and the persisted part of R.” (3) §9 and §10 use Sworld. 2. Domain state XtX_t

For an AI R&D OS, domain objects include sources, projects, experiments, artifacts, people, models, and tools. Let the entities be typed:

Vt=⋃τ∈𝒯Vtτ,𝒯={Source,Project,Person,Workflow,Model,Experiment,…}.V_t=\bigcup_{\tau\in\mathcal T}V_t^\tau, \qquad \mathcal T=\{\mathrm{Source},\mathrm{Project},\mathrm{Person},\mathrm{Workflow},\mathrm{Model},\mathrm{Experiment},\ldots\}.

Use a typed, attributed graph for the conceptual domain model:

Xt=Gt=(Vt,Lt,ϕt),Lt⊆Vt×ℛrel×Vt.X_t=G_t=(V_t,L_t,\phi_t), \qquad L_t\subseteq V_t\times\mathcal R_{\mathrm{rel}}\times V_t.

Here LtL_t is a set of labeled edges, ℛrel\mathcal R_{\mathrm{rel}} is the set of relation types, and ϕt(v)\phi_t(v) contains the attributes of entity vv. For example:

(SourceVideo,contains,Workflow42),(Workflow42,uses,Opus5.5),(Project7,implements,Workflow42). (\mathrm{SourceVideo},\mathrm{contains},\mathrm{Workflow42}), \quad (\mathrm{Workflow42},\mathrm{uses},\mathrm{Opus5.5}), \quad (\mathrm{Project7},\mathrm{implements},\mathrm{Workflow42}).

This does not require a graph database: relational tables can implement the same typed graph.

Reviewer notes · §2 · Domain state

R10StrengthA typed, attributed graph is the right conceptual model. The examples come from real use (SourceVideo, Workflow42, Opus5.5), which makes the definitions checkable. The note that relational tables can implement it is correct and keeps the build small.
R11WeaknessWorkflow is a domain type in 𝒯 (§2) and also process state Wt (§4). The edge (Project7, implements, Workflow42) treats Workflow42 as a domain entity. The document does not say whether Wt(42) is the same object.
R11 fixRecommendationR12 gives the split. Concrete: in 𝒯, replace Workflow with WorkflowDef. In §4, Wt(j) is run j. Add the edge (run j, instance_of, WorkflowDef k) in X. Then Workflow42 is a WorkflowDef, and each new video ingestion creates a new run.
R12SuggestionSplit definition from run. A Workflow node in X is a versioned definition (a template). A WorkflowRun in W is one execution with its own qt. One definition has many runs. Most workflow engines use this class/instance split.
R13WeaknessPerson is an entity type in X, and human actors form ℐH (§8). The link between a Person node and an actor in ℐH is not stated. Authorization (§6) needs this link: a rule attached to a Person must reach the actor who acts.
R13 fixRecommendationAdd an Actor entity type to 𝒯 and a one-to-one map between Actor nodes and ℐ. A human Actor node links to its Person node. Authorization rules refer to Actor nodes. The provenance agent nodes (R81) are the same Actor nodes, so one object answers “who acted”.
R14Weakness(Workflow42, uses, Opus5.5) changes over time because models change version. Say whether a version upgrade creates a new entity or changes an attribute. The answer matters for §9, because the kernel T changes when the model changes (see R46).
R14 fixRecommendationMake each model version its own immutable entity: Opus5.5 is one node, and a later version is a new node. Give the edge (Workflow42, uses, …) a valid-from timestamp. An upgrade is then an event that moves the edge, and the log shows exactly when T changed (see R46).

3. Knowledge state KtK_t

A stored statement need not be true. Represent a knowledge record as

ki=(ci,σi,γi,πi,ti),Kt={k1,…,kn},k_i=(c_i,\sigma_i,\gamma_i,\pi_i,t_i), \qquad K_t=\{k_1,\ldots,k_n\},

where cic_i is a proposition or claim, σi\sigma_i its source, γi∈[0,1]\gamma_i\in[0,1] a confidence assessment, πi\pi_i its provenance, and tit_i a timestamp. For example, “Workflow X reduces implementation latency” may have estimated confidence γi=0.71\gamma_i=0.71 rather than being stored as unquestioned fact.

Epistemic rule: data ≠\ne belief ≠\ne verified fact. A numeric confidence is meaningful only if its interpretation and calibration are specified; otherwise it is an annotation, not a probability theorem.

Reviewer notes · §3 · Knowledge state

R15StrengthThe epistemic rule and the calibration caveat are the most precise statements in the document. Treating γi as an annotation unless its calibration is specified is correct.
R16Weaknessσi (source) and πi (provenance) overlap. A source is the first node of a provenance chain. §16 then adds Πt as a separate DAG. So three places record where a claim came from.
R16 fixRecommendationR17 gives the fix. Concrete: the claim record becomes kn = (cn, κn, sn, tn), where sn is the node in Πt that produced the claim. Delete πi from §3.
R17SuggestionKeep σi as a pointer into Πt and drop πi. Then “Why do you believe this?” (§16) reads one structure.
R18WeaknessKt is a set with no update rule. Real claims are contradicted, superseded, and retracted. In a plain set, a new claim “Workflow X does not reduce latency” sits next to the old claim with no link between them.
R18 fixRecommendationR19 gives the fields. Formal version: Kt = (Ct, supersedest, contradictst, statust). Ct is the set of claim records. supersedes and contradicts are relations on Ct. statust: Ct → {active, superseded, retracted}. A retraction is an event that changes status and never deletes. Queries show active claims by default.
R19SuggestionAdd typed relations between claims: supports, contradicts, supersedes. Add a status field: active, superseded, retracted. Do not delete old claims, because the event log (§11) needs them for replay.
R20WeaknessClaims ci do not reference entities in X. “Workflow X reduces implementation latency” names Workflow X only in its text. Without a typed link, the query “all claims about Workflow42” becomes a text search.
R20 fixRecommendationAdd a field aboutn ⊆ Vt to each claim: the entities the claim is about. Store it as edges (claim, about, entity). The extraction agent fills it when it creates the claim. Then “all claims about Workflow42” is a graph query, not a text search.
R21Weakness“Belief” has two meanings. Here it is a stored claim in Kt: one shared copy for all actors. In §10, bti is private to actor i and is a distribution over St. §18 calls Bt “claims, beliefs”. Use “claim” for the stored record and “belief” for the actor’s private state.
R21 fixRecommendationIn §18, rename Bt to “claims and confidence assessments” and remove “beliefs”. Keep “belief” and bti for §10 only. Add one sentence to §10: “A claim in Kt is shared data. A belief bti is private to actor i. An agent can use claims as evidence for its belief.”

4. Workflow state WtW_t

An evolving process is more than a static entity. A workflow jj can be represented by a finite-state machine, DAG, or Petri net:

Wt(j)=(qt(j),Dt(j)),qt(j)∈Qj,qt+1(j)=δj(qt(j),at).W_t^{(j)}=(q_t^{(j)},D_t^{(j)}), \qquad q_t^{(j)}\in Q_j, \qquad q_{t+1}^{(j)}=\delta_j(q_t^{(j)},a_t).

For transcript ingestion, QjQ_j might contain raw, parsed, summarized, workflow-extracted, reviewed, and implemented. Dependencies, concurrent tasks, and retries may need a richer formalism than a single finite-state machine. Explicit process state avoids an unstructured pile of Boolean flags.

Reviewer notes · §4 · Workflow state

R22StrengthExplicit process state instead of a pile of Boolean flags is a correct and practical rule. The statement that dependencies, concurrency, and retries may need more than one finite-state machine is honest.
R23WeaknessDt(j) is never defined. From context it can mean data, dependencies, or a deadline.
R23 fixRecommendationDefine Dt(j) as the run data: Dt(j) = (inputs, outputs, attempts) of run j. If the author meant dependencies, give them their own symbol, for example Dep ⊆ runs × runs, and say that a run starts only when its dependencies are in a done state.
R24Weaknessδj(q, at) accepts every action at, but most actions do not touch workflow j. Define δj(q, a) = q for actions outside workflow j. As written, the equation lets every action move every workflow.
R24 fixRecommendationReplace the equation with: qt+1(j) = δj(qt(j), at) if at ∈ 𝒜(j), else qt(j). 𝒜(j) is the set of actions that name run j. In code this is a filter: the workflow reducer handles only events that carry its run id.
R25SuggestionThe example list has only success states: raw → parsed → summarized → workflow-extracted → reviewed → implemented. Add failed, cancelled, and waiting_approval. The waiting_approval state is where §14’s proposals live (see R72).

5. Agent runtime state RtR_t

For agent ii, define

Rti=(gti,mti,cti,πti,hti,τti),Rt=(Rt1,…,RtN),R_t^i=(g_t^i,m_t^i,c_t^i,\pi_t^i,h_t^i,\tau_t^i), \qquad R_t=(R_t^1,\ldots,R_t^N),

where gg is the goal, mm memory, cc active context, π\pi the policy or strategy, hh execution history, and τ\tau the available tools. Two identical domain databases can produce different future behavior if the agents have different goals or memory. This runtime state can be partly ephemeral, but it must be included when the model aims to predict the next transition.

Reviewer notes · §5 · Agent runtime state

R26Strength“Two identical domain databases can produce different future behavior” is the sentence that justifies Rt. It is correct, and it is the main difference from a classical application.
R27Weaknessπti here is the agent’s strategy. §6 uses “policy” for authorization. The same word has two meanings in two consecutive sections.
R27 fixRecommendationRename the agent’s πti to “strategy” ψti (R9). Use “policy” only for authorization. After the rename, search the text for “policy” and check each use; §5 and §13 are the places at risk.
R28WeaknessThe goal gti (§5) and the objective Ui (§13) are not connected. Is g a target state, a predicate on states, or a text prompt? If g is text, Ui cannot be computed from it.
R28 fixRecommendationDefine the goal as a predicate on owned states: gti: 𝒮owned → {0, 1}, “the task is done”. Keep the natural-language task text as a separate field, the task description. State who decides whether g holds: a human, a test, or an evaluator. Ui can then include a reward for g = 1 minus costs (see R66). This makes the gap between the text and the predicate visible.
R29WeaknessModel identity (for example Opus 5.5 against a later version) and the system prompt are not in Rti. Both change behavior as much as memory does. Today the model appears only as an entity in X (§2).
R29 fixRecommendationAdd 2 fields: Rti = (model_id, prompt_id, g, mem, ctx, ψ, h). model_id and prompt_id point to immutable entities in X (R14). Every event records the model_id and prompt_id of the actor that produced it. A replay or an audit then knows which model produced each result.
R30WeaknessHuman actors have no runtime state. Human goals, memory, and attention are not modeled, so human actions enter T as exogenous inputs. State this. It means T can respond to human actions but cannot predict them.
R30 fixRecommendationAdd to §5: “Human actors have no modeled runtime state. Their actions are exogenous inputs: T is defined for a given action, but the theory does not predict which action a human takes.” This keeps the theory small and honest. Add a human model only if you later need to predict human actions.
R31WeaknessTools τti duplicate admissibility 𝒜i(St) (§6). An available tool is a family of admissible actions. Keep one of the two.
R31 fixRecommendationRemove the tools field from Rti. Define the tool set as derived: toolsi(St) = the action families with at least one admissible action in 𝒜i(St). In the implementation, generate the tool list shown to the agent from the policy, so the two cannot disagree.

6. Policy state PtP_t

Not every action is valid. Define state-dependent admissibility:

𝒜i(St)⊆𝒜i,at∈𝒜i(St),\mathcal A_i(S_t)\subseteq\mathcal A_i, \qquad a_t\in\mathcal A_i(S_t),

or an authorization predicate

Pt(St,i,a)∈{0,1}.P_t(S_t,i,a)\in\{0,1\}.

For instance, an agent may draft a report but require human authorization to publish it. The policy is part of the system’s operational state if permissions and approvals can change over time.

Reviewer notes · §6 · Policy state

R32StrengthState-dependent admissibility is the correct form. Treating permissions that change over time as state is correct.
R33SuggestionThe two forms are equivalent: 𝒜i(S) = { a ∈ 𝒜i : Pt(S, i, a) = 1 }. Say so and keep one. Also, Pt is a state component (§1) and a function that takes St, which contains Pt. That is valid, but then the subscript t in Pt(St, …) is redundant.
R34WeaknessThere is no principal. In practice an agent acts on behalf of a human with that human’s credentials, for example a GitHub token. The model has actors but no “acts for” relation. Without it, the audit trail cannot answer “who authorized this agent to do this?”
R34 fixRecommendationR35 gives the permission rule. Also add principal to every event: et = (actor, principal, action, arguments, result, timestamp, provenance). For a chain (agent A starts sub-agent B), set principal(B) = principal(A), not A. Authority then never grows along a chain.
R35SuggestionAdd principal: ℐA → ℐH and require P(S, i, a) = 1 ⇒ P(S, principal(i), a) = 1. An agent then never has more permission than its principal. This one implication closes the most common escalation path.

7. External state EtE_t

The application interacts with GitHub, Drive, the web, deployment services, email, and APIs. Distinguish external reality from the app’s last observation:

EtrealversusÊt.E_t^{\mathrm{real}} \qquad\text{versus}\qquad \widehat E_t.

A local cache can be stale. If StS_t denotes the complete modeled world, it may contain EtrealE_t^{\mathrm{real}}; if StS_t denotes only the application’s stored state, it contains merely Êt\widehat E_t. Fix this boundary before claiming the system is Markovian.

Reviewer notes · §7 · External state

R36StrengthEreal against Ê is correct and important. A stale local copy of external state is a common cause of wrong agent actions.
R37WeaknessThe instruction “Fix this boundary before claiming the system is Markovian” is not carried out anywhere in the document (see R5). “Markovian” is also never defined. Define it once: T depends on the past only through St.
R37 fixRecommendationAdd a definition to §9: “A process is Markov on a state description Z if Pr(Zt+1 | Z0:t, a0:t) = Pr(Zt+1 | Zt, at).” Then state: Markov on Sworld by construction; in general not Markov on Sowned (R6). Change the §7 sentence to “See §9 for which state is Markov.”
R38WeaknessIrreversible actions are not treated. Sending an email, pushing to a public repository, or making a payment changes Ereal, and no owned inverse exists. Event sourcing (§11) can rebuild owned state but cannot undo these actions.
R38 fixRecommendationR39 gives the classes. Also add a field to each action type: effect ∈ {owned, external-reversible, external-compensable, external-irreversible}. Add one default rule: effect = external-irreversible ⇒ class = approval, unless an explicit rule says free. For compensable actions, store the compensating action type, so the system can offer the undo.
R39SuggestionClassify each action as reversible (an owned inverse exists), compensable (a correcting action exists, for example a retraction post), or irreversible. Then §14’s partition has a stated reason: irreversible external actions go to 𝒜approval by default.
R40SuggestionRecord the observation time of each part of Êt (last_synced_at). An invariant can then block high-risk actions that depend on Ê older than a set age.

8. Actors

Let

ℐ=ℐH∪ℐA∪ℐS\mathcal I=\mathcal I_H\cup\mathcal I_A\cup\mathcal I_S

be human actors, AI agents, and autonomous software services. Actor ii has action space 𝒜i\mathcal A_i. A concurrent joint action can be written

At=(at1,…,atn),St+1=F(St,At).A_t=(a_t^1,\ldots,a_t^n), \qquad S_{t+1}=F(S_t,A_t).

Human and agent actions may enter through different interfaces while affecting the same domain state.

Reviewer notes · §8 · Actors

R41WeaknessThree action models appear, and they conflict. (1) §0: one action at from 𝒜human ∪ 𝒜agent, actor unknown. (2) §8–§9: a joint action At = (at1, …, atn), all actors act in the same step. (3) §18: one action at with actor it. §15 then serializes actions, which fits (3) and not (2).
R41 fixRecommendationR42 gives the model. Concrete edits: delete the joint action At from §8 and §9. Replace the §8 equation with St+1 ∼ T(· | St, it, at). Add a remark: “Simultaneous actions become an interleaving in commit order. §15 handles two actions that read the same version.” Then §0, §8, §9, and §18 all use (it, at).
R42SuggestionUse interleaving semantics. t is the position in the committed event log. Each step has exactly one actor and one action, (it, at). Concurrency then appears as the order of commits and as merges (§15). This also defines t (see R2) and matches the event model of §11. Keep joint actions only for true simultaneity, which an application with one commit point does not have.
R43WeaknessChanges that no actor makes have no actor: a GitHub repository changes, an API goes down, time passes. Add an environment actor (“nature”) to ℐ, or state that T contains these changes.
R43 fixRecommendationAdd an actor env: ℐ = ℐH ∪ ℐA ∪ ℐS ∪ {env}. Its actions are observed external changes, for example ExternalChanged(resource, new_value, observed_at). They enter the log like other events. In practice they come from webhooks and sync jobs.

9. Stochastic transitions

APIs fail, models vary, and the environment changes. Replace the deterministic function with a transition kernel:

St+1∼T(⋅∣St,At),T:𝒮×𝒜→Δ(𝒮).S_{t+1}\sim T(\,\cdot\mid S_t,A_t), \qquad T:\mathcal S\times\mathcal A\longrightarrow\Delta(\mathcal S).

Δ(𝒮)\Delta(\mathcal S) denotes distributions over future states. Deterministic FF is the special case T(⋅∣S,A)=δF(S,A)T(\cdot\mid S,A)=\delta_{F(S,A)}, a point mass.

Reviewer notes · §9 · Stochastic transitions

R44StrengthThe kernel form is correct, and the deterministic case as a point mass is stated correctly.
R45Weakness𝒜 in T: 𝒮×𝒜 → Δ(𝒮) is never defined. For joint actions it would be ∏i 𝒜i. For interleaving it is ⋃i {i}×𝒜i.
R45 fixRecommendationDefine 𝒜 := ⋃i ∈ ℐ {i} × 𝒜i, so each action carries its actor. Then T: 𝒮 × 𝒜 → Δ(𝒮) is well-typed and matches the interleaving model (R42).
R46WeaknessT has no time index, so it is assumed stationary. It is not: a model upgrade, a new tool, or an API change alters T. Either put model and tool versions into St (then T can stay fixed) or write Tt.
R46 fixRecommendationKeep T time-invariant and put all versions into the state: model_id and prompt_id (R29), tool versions, and API versions, as entities in X. A version change is then an ordinary event. This is better than writing Tt, because the log shows when behavior changed and a replay knows which version applied.

15. Concurrency

Two agents may act on the same state. One solution serializes the actions:

St→aiSt+1→ajSt+2.S_t\xrightarrow{a_i}S_{t+1}\xrightarrow{a_j}S_{t+2}.

Another merges compatible concurrent updates:

St+1=M(Fi(St,ai),Fj(St,aj)).S_{t+1}=M(F_i(S_t,a_i),F_j(S_t,a_j)).

Some replicated data supports a CRDT-style join ⊔\sqcup with

x⊔y=y⊔x,(x⊔y)⊔z=x⊔(y⊔z),x⊔x=x.x\sqcup y=y\sqcup x, \qquad (x\sqcup y)\sqcup z=x\sqcup(y\sqcup z), \qquad x\sqcup x=x.

These properties yield convergence for the relevant data type. They do not make arbitrary business operations commute: publication, payments, and uniqueness constraints generally require coordination or transactions.

A further mathematical direction

One can study a category whose objects are valid states and whose morphisms are permitted transitions Si→aSjS_i\xrightarrow{a}S_j. Workflow sequencing corresponds to composition when transitions are composable. This is a possible formal extension, not a result established by the model above: stochastic actions, concurrency, observations, and authorization need careful treatment before claiming a full categorical theory.
