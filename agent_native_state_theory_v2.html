The starting point is

St+1=F(St,it,at),it∈ℐ,at∈𝒜it(St).S_{t+1}=F(S_t,i_t,a_t), \qquad i_t\in\mathcal I,\quad a_t\in\mathcal A_{i_t}(S_t).

A human and an agent can change the same underlying application state. Each step names its actor iti_t, because the same action type, for example editing a document, is available to humans and to agents. A rigorous account extends this equation to a partially observable, multi-actor controlled dynamical system with typed state, provenance, permissions, and constrained transitions. The simple deterministic equation is a special case.

Time. The index t∈ℕt\in\mathbb N counts committed events: step tt is the tt-th entry of the event log (§11). Wall-clock time is an attribute of each event, not the index. Actions that occur at the same wall-clock moment are ordered by their commit (§8, §15).

1. State space

Let Stworld∈𝒮S_t^{\mathrm{world}}\in\mathcal S be the complete state of the modeled world: everything that affects the next transition. Begin with a product decomposition:

𝒮=𝒳×𝒦×𝒲×ℛ×𝒫×𝒟×ℰ,Stworld=(Xt,Kt,Wt,Rt,Pt,Πt,Et).\mathcal S=\mathcal X\times\mathcal K\times\mathcal W\times\mathcal R\times\mathcal P\times\mathcal D\times\mathcal E, \qquad S_t^{\mathrm{world}}=(X_t,K_t,W_t,R_t,P_t,\Pi_t,E_t).

Component Meaning
XtX_t Domain and operational state (§2)
KtK_t Claims and their confidence assessments (§3)
WtW_t Workflow runs and process state (§4)
RtR_t Runtime state of agents (§5)
PtP_t Policies and permissions (§6)
Πt\Pi_t Provenance graph (§16); 𝒟\mathcal D is the set of such graphs
Et=(Etreal,Êt)E_t=(E_t^{\mathrm{real}},\widehat E_t) External reality and the app’s last observation of it (§7)

These components have different semantics even when stored in the same database. Invariants are not a state component; they form the fixed set 𝒞\mathcal C (§12, §17).

Coupling

The product is the type of SS. It does not make the components independent. One transition can update several components, and the invariants in 𝒞\mathcal C relate them: for example, published⇒human_approved\mathrm{published}\Rightarrow\mathrm{human\_approved} (§12) links workflow state and policy state. One commit updates all affected components atomically: one transaction per event, not one per component.

World state and owned state

The application stores only part of the world:

Stowned=ω(Stworld)=(Xt,Kt,Wt,Rtpers,Pt,Πt,Êt).S_t^{\mathrm{owned}}=\omega\!\left(S_t^{\mathrm{world}}\right)=\left(X_t,K_t,W_t,R_t^{\mathrm{pers}},P_t,\Pi_t,\widehat E_t\right).

The projection ω\omega keeps what the application stores and can replay. Under proposal representation E1 (§14), StownedS_t^{\mathrm{owned}} has an eighth component Propt\mathrm{Prop}_t; under E2, proposals are part of WtW_t. The projection drops EtrealE_t^{\mathrm{real}}, the ephemeral part RtephR_t^{\mathrm{eph}} of agent runtime state (§5), and all unmodeled state, such as human intentions. Without a superscript, StS_t means StworldS_t^{\mathrm{world}}. §9 and §10 are stated on SworldS^{\mathrm{world}}. §11 to §16 are stated on SownedS^{\mathrm{owned}}, because those sections describe what the application can check, store, and replay.

2. Domain state XtX_t

For an AI R&D OS, domain objects include sources, projects, experiments, artifacts, people, actors, models, prompts, and tools. Let the entities be typed:

Vt=⋃τ∈𝒯Vtτ,𝒯={Source,Project,Person,Actor,WorkflowDef,Model,Prompt,Experiment,…}.V_t=\bigcup_{\tau\in\mathcal T}V_t^\tau, \qquad \mathcal T=\{\mathrm{Source},\mathrm{Project},\mathrm{Person},\mathrm{Actor},\mathrm{WorkflowDef},\mathrm{Model},\mathrm{Prompt},\mathrm{Experiment},\ldots\}.

Use a typed, attributed graph for the conceptual domain model:

Xt=(Vt,Lt,ϕt),Lt⊆Vt×Rel×Vt.X_t=(V_t,L_t,\phi_t), \qquad L_t\subseteq V_t\times\mathrm{Rel}\times V_t.

Here LtL_t is a set of labeled edges, Rel\mathrm{Rel} is the set of relation types, and ϕt(v)\phi_t(v) contains the attributes of entity vv. For example:

(SourceVideo,contains,Workflow42),(Workflow42,uses,Opus5.5),(Project7,implements,Workflow42). (\mathrm{SourceVideo},\mathrm{contains},\mathrm{Workflow42}), \quad (\mathrm{Workflow42},\mathrm{uses},\mathrm{Opus5.5}), \quad (\mathrm{Project7},\mathrm{implements},\mathrm{Workflow42}).

This does not require a graph database: relational tables can implement the same typed graph.

Definitions and runs

A WorkflowDef\mathrm{WorkflowDef} node is a versioned definition, a template. One execution of it is a run in WtW_t (§4). One definition has many runs, and each run records the definition it instantiates. In the example, Workflow42\mathrm{Workflow42} is a definition; each new video ingestion creates a new run.

Actors as entities

Each actor in ℐ\mathcal I (§8) has exactly one Actor\mathrm{Actor} node. A human’s Actor\mathrm{Actor} node links to that human’s Person\mathrm{Person} node. Authorization rules (§6) and provenance agent nodes (§16) refer to Actor\mathrm{Actor} nodes, so one object answers the question “who acted”.

Versions as entities

Each model version and each prompt version is its own immutable node: Opus5.5\mathrm{Opus5.5} is one node, and a later version is a new node. Edges such as (Workflow42,uses,Opus5.5)(\mathrm{Workflow42},\mathrm{uses},\mathrm{Opus5.5}) carry a valid-from timestamp. An upgrade is an event that moves the edge, so the log shows when behavior changed (§9).

3. Knowledge state KtK_t

A stored statement need not be true. Represent a claim record as

kn=(cn,srcn,κn,aboutn,tn),Kt=(Claimst,supportst,contradictst,supersedest,statust),k_n=(c_n,\mathrm{src}_n,\kappa_n,\mathrm{about}_n,t_n), \qquad K_t=\left(\mathrm{Claims}_t,\ \mathrm{supports}_t,\ \mathrm{contradicts}_t,\ \mathrm{supersedes}_t,\ \mathrm{status}_t\right),

where cnc_n is a proposition or claim, srcn∈Nt\mathrm{src}_n\in N_t the node in the provenance graph Πt\Pi_t (§16) that produced it, κn∈[0,1]\kappa_n\in[0,1] a confidence assessment, aboutn⊆Vt\mathrm{about}_n\subseteq V_t the entities the claim is about, and tnt_n a timestamp. Claimst\mathrm{Claims}_t is the set of claim records. supportst\mathrm{supports}_t, contradictst\mathrm{contradicts}_t, and supersedest\mathrm{supersedes}_t are relations on Claimst\mathrm{Claims}_t, and statust:Claimst→{active,superseded,retracted}\mathrm{status}_t:\mathrm{Claims}_t\to\{\mathrm{active},\mathrm{superseded},\mathrm{retracted}\}. For example, “Workflow X reduces implementation latency” may have estimated confidence κn=0.71\kappa_n=0.71 rather than being stored as unquestioned fact, with aboutn={WorkflowX}\mathrm{about}_n=\{\mathrm{Workflow\ X}\}.

Epistemic rule: data ≠\ne claim ≠\ne verified fact. A numeric confidence is meaningful only if its interpretation and calibration are specified; otherwise it is an annotation, not a probability theorem.

Update rule. A retraction or a supersession is an event that changes statust\mathrm{status}_t. It never deletes a record, because replay (§11) needs every record. Queries return active claims by default.

Subjects. aboutn\mathrm{about}_n is stored as edges (claim,about,entity)(\mathrm{claim},\mathrm{about},\mathrm{entity}), filled by the actor that creates the claim. “All claims about Workflow42” is then a graph query, not a text search.

Estimates are claims. Measured or estimated quantities, such as an evaluation score (§11) or a router estimate (§13), are claims with a source and a confidence.

4. Workflow state WtW_t

An evolving process is more than a static entity. A workflow run jj can be represented by a finite-state machine, DAG, or Petri net:

Wt(j)=(dj,qt(j),Dt(j)),qt(j)∈Qj,qt+1(j)={ηj(qt(j),at)at∈𝒜(j),qt(j)otherwise.W_t^{(j)}=\left(d_j,\,q_t^{(j)},\,D_t^{(j)}\right), \qquad q_t^{(j)}\in Q_j, \qquad q_{t+1}^{(j)}=\begin{cases}\eta_j\!\left(q_t^{(j)},a_t\right) & a_t\in\mathcal A^{(j)},\\ q_t^{(j)} & \text{otherwise.}\end{cases}

Here djd_j is the WorkflowDef\mathrm{WorkflowDef} that run jj instantiates (§2), Dt(j)=(inputs,outputs,attempts)D_t^{(j)}=(\mathrm{inputs},\mathrm{outputs},\mathrm{attempts}) is the run’s data, and 𝒜(j)\mathcal A^{(j)} is the set of actions that name run jj. An action that does not name run jj leaves it unchanged; in code, a workflow reducer handles only events that carry its run id.

For transcript ingestion, QjQ_j might contain raw, parsed, summarized, workflow-extracted, waiting_approval, reviewed, implemented, failed, and cancelled. The last three states matter: waiting_approval holds runs that wait for a human (§14), and failed and cancelled are where runs end when they do not succeed. Dependencies between runs form a relation Dep⊆runs×runs\mathrm{Dep}\subseteq\mathrm{runs}\times\mathrm{runs}; a run starts only when every run it depends on is in a done state. Concurrent tasks and retries may need a richer formalism than a single finite-state machine. Explicit process state avoids an unstructured pile of Boolean flags.

5. Agent runtime state RtR_t

For agent ii, define

Rti=(modelti,promptti,gti,memti,ctxti,hti),Rt=(Rti)i∈ℐA,R_t^i=\left(\mathrm{model}_t^i,\mathrm{prompt}_t^i,g_t^i,\mathrm{mem}_t^i,\mathrm{ctx}_t^i,h_t^i\right), \qquad R_t=\left(R_t^i\right)_{i\in\mathcal I_A},

where model\mathrm{model} and prompt\mathrm{prompt} point to immutable Model\mathrm{Model} and Prompt\mathrm{Prompt} entities in XtX_t (§2), gg is the goal, mem\mathrm{mem} memory, ctx\mathrm{ctx} active context, and hh execution history. The agent’s strategy ψti\psi_t^i, the rule by which it chooses actions, is induced by model, prompt, memory, and context; it is not stored separately. Two identical domain databases can produce different future behavior if the agents have different goals, memory, or models.

Goal. The goal is a predicate on owned states, gti:𝒮owned→{0,1}g_t^i:\mathcal S^{\mathrm{owned}}\to\{0,1\}, meaning “the task is done”. The natural-language task text is a separate field, the task description. The task states who decides whether gg holds: a human, a test, or an evaluator. This makes the gap between the text and the predicate visible.

Persistent and ephemeral parts. Rtpers=(model,prompt,g,mem,h)R_t^{\mathrm{pers}}=(\mathrm{model},\mathrm{prompt},g,\mathrm{mem},h) is stored and belongs to SownedS^{\mathrm{owned}}. Rteph=ctxR_t^{\mathrm{eph}}=\mathrm{ctx} belongs to SworldS^{\mathrm{world}} only. The ephemeral part must still be included when the model aims to predict the next transition (§9).

Tools. Tools are not a separate field. The tools of agent ii are the action families with at least one admissible action, derived from policy: toolsi(S)={families of 𝒜i(S)}\mathrm{tools}_i(S)=\{\text{families of }\mathcal A_i(S)\} (§6). An implementation generates the tool list shown to the agent from the policy, so the two cannot disagree.

Human actors have no modeled runtime state. Their actions are exogenous inputs: TT (§9) is defined for a given action, but the theory does not predict which action a human takes.

6. Policy state PtP_t

Not every action is valid. Define state-dependent admissibility:

𝒜i(S)⊆𝒜i,at∈𝒜it(St),\mathcal A_i(S)\subseteq\mathcal A_i, \qquad a_t\in\mathcal A_{i_t}(S_t),

or an authorization predicate

auth(S,i,a)∈{0,1},𝒜i(S)={a∈𝒜i:auth(S,i,a)=1}.\mathrm{auth}(S,i,a)\in\{0,1\}, \qquad \mathcal A_i(S)=\{a\in\mathcal A_i:\mathrm{auth}(S,i,a)=1\}.

The two forms are equivalent; this document uses both names for the same object. auth\mathrm{auth} reads the policy component PtP_t of SownedS^{\mathrm{owned}}, so it needs no time subscript of its own. For instance, an agent may draft a report but require human authorization to publish it (§14). The policy is part of the system’s operational state if permissions and approvals can change over time. How PtP_t itself may change is fixed by the rule Meta\mathrm{Meta} (§17).

Principals

An agent acts on behalf of a human, often with that human’s credentials. Define

principal:ℐA∪ℐS→ℐH,auth(S,i,a)=1⇒auth(S,principal(i),a)=1.\mathrm{principal}:\mathcal I_A\cup\mathcal I_S\to\mathcal I_H, \qquad \mathrm{auth}(S,i,a)=1\ \Longrightarrow\ \mathrm{auth}\!\left(S,\mathrm{principal}(i),a\right)=1.

An agent never has more permission than its principal. When agent AA starts sub-agent BB, principal(B)=principal(A)\mathrm{principal}(B)=\mathrm{principal}(A), so authority does not grow along a chain. Every event records the principal (§11), so the audit question “who authorized this?” has a direct answer.

7. External state EtE_t

The application interacts with GitHub, Drive, the web, deployment services, email, and APIs. Distinguish external reality from the app’s last observation:

EtrealversusÊt.E_t^{\mathrm{real}} \qquad\text{versus}\qquad \widehat E_t.

A local cache can be stale. EtrealE_t^{\mathrm{real}} is part of SworldS^{\mathrm{world}}; Êt\widehat E_t is part of SownedS^{\mathrm{owned}} (§1). Which of the two states is Markov is settled in §9.

Freshness. Each part of Êt\widehat E_t records its observation time, last_synced_at\mathrm{last\_synced\_at}. A rule in PtP_t can block a high-risk action that depends on an observation older than a set age.

Effects and reversibility

Classify every action type by its effect:

effect(a)∈{owned,ext-reversible,ext-compensable,ext-irreversible}.\mathrm{effect}(a)\in\{\mathrm{owned},\ \mathrm{ext\text{-}reversible},\ \mathrm{ext\text{-}compensable},\ \mathrm{ext\text{-}irreversible}\}.

An owned effect changes only SownedS^{\mathrm{owned}} and has an inverse there. An external reversible effect has an exact external inverse. An external compensable effect has a correcting action, for example a retraction post; the action type stores its compensating action type, so the system can offer the undo. An external irreversible effect, such as sending an email, pushing to a public repository, or making a payment, has neither. Event sourcing (§11) can rebuild owned state but cannot undo external effects. Default rule: effect(a)=ext-irreversible⇒class(S,i,a)=approval\mathrm{effect}(a)=\mathrm{ext\text{-}irreversible}\Rightarrow\mathrm{class}(S,i,a)=\mathrm{approval} unless an explicit rule in PtP_t says otherwise (§14).

8. Actors

Let

ℐ=ℐH∪ℐA∪ℐS∪{env}\mathcal I=\mathcal I_H\cup\mathcal I_A\cup\mathcal I_S\cup\{\mathrm{env}\}

be human actors, AI agents, autonomous software services, and the environment. Actor ii has action space 𝒜i\mathcal A_i. The environment actor records changes that no other actor makes, such as a repository change or an API outage, as observed events, for example ExternalChanged(resource,new_value,observed_at)\mathrm{ExternalChanged}(\mathrm{resource},\mathrm{new\_value},\mathrm{observed\_at}). In practice these come from webhooks and sync jobs.

Interleaving semantics. Each step has exactly one actor and one action:

St+1=F(St,it,at).S_{t+1}=F(S_t,i_t,a_t).

Actions that occur at the same wall-clock moment become an interleaving in commit order. When two actions read the same state version, §15 decides whether both commit. A joint action of all actors in one step is not used: an application with one commit point never needs it.

Human and agent actions may enter through different interfaces while affecting the same domain state (§18).

9. Stochastic transitions

APIs fail, models vary, and the environment changes. Replace the deterministic function with a transition kernel:

𝒜=⋃i∈ℐ{i}×𝒜i,St+1∼T(⋅∣St,it,at),T:𝒮×𝒜→Δ(𝒮).\mathcal A=\bigcup_{i\in\mathcal I}\{i\}\times\mathcal A_i, \qquad S_{t+1}\sim T(\,\cdot\mid S_t,i_t,a_t), \qquad T:\mathcal S\times\mathcal A\longrightarrow\Delta(\mathcal S).

Δ(𝒮)\Delta(\mathcal S) denotes distributions over future states. Deterministic FF is the special case T(⋅∣S,i,a)=δF(S,i,a)T(\cdot\mid S,i,a)=\delta_{F(S,i,a)}, a point mass.

Stationarity. TT has no time index. This is correct only because every version that changes behavior is in the state: model and prompt (§5), tool versions, and API versions are entities in XtX_t (§2). A version change is an ordinary event, and the log shows when behavior changed.

Markov property. A process is Markov on a state description ZZ if

Pr⁡(Zt+1∣Z0:t,i0:t,a0:t)=Pr⁡(Zt+1∣Zt,it,at).\Pr\!\left(Z_{t+1}\mid Z_{0:t},i_{0:t},a_{0:t}\right)=\Pr\!\left(Z_{t+1}\mid Z_t,i_t,a_t\right).

The process is Markov on SworldS^{\mathrm{world}} by construction, because SworldS^{\mathrm{world}} contains everything that affects the next transition. In general it is not Markov on SownedS^{\mathrm{owned}}: the dropped parts, ErealE^{\mathrm{real}}, agent context, and human intentions, carry information from the past.

Status of TT. TT is a specification device. It defines which outcomes are possible, its support, which §12 and §20 use. It is not a predictive model: SworldS^{\mathrm{world}} includes agent context, so the state space is too large to estimate transition probabilities. Probabilities are estimated only for small projections that have data, for example Pr⁡(tool call fails∣tool,model)\Pr(\text{tool call fails}\mid\text{tool},\text{model}) counted from the event log.

10. Partial observability

An actor rarely observes all of StS_t. Actor ii receives

oti∼Oi(⋅∣St)o_t^i\sim O_i(\,\cdot\mid S_t)

and can maintain the belief state

bti(s)=Pr⁡(St=s∣o1:ti,a1:t−1i).b_t^i(s)=\Pr\!\left(S_t=s\mid o_{1:t}^i,a_{1:t-1}^i\right).

The actual state StS_t and the actor’s model btib_t^i are distinct. An LLM’s context is one input to that model. If active context affects future action selection, its contents are also part of agent runtime state RtiR_t^i; these are complementary descriptions at different levels.

Assumption. This formula conditions only on actor ii’s own observations and actions. It is exact when each actor treats the other actors as part of the environment, with actions drawn from a fixed unknown distribution. The assumption fails when agents adapt to each other; in that case they coordinate through the shared log and version checks (§15), not through models of each other’s beliefs.

Normative status. btib_t^i is the belief a correct Bayesian agent would hold. An LLM agent approximates it from its context, and nothing checks the approximation. So safety never relies on an agent’s belief; it relies on version checks (§14, §15) and invariants (§12).

Read versions. Every observation of owned state carries the version it read. An agent keeps a read in its context for minutes, much longer than a human keeps a form open, so the read version travels with every write the agent makes (§15).

Observation parity. For the part of SownedS^{\mathrm{owned}} that an action depends on, the human interface and the agent interface expose the same content, in different formats (§19, N2). An agent and a human that see different projections of the same state are a common source of wrong actions.

11. Events as an implementation primitive

Define an event as

et=(actor,principal,action,arguments,result,model,schema_version,timestamp,provenance).e_t=(\mathrm{actor},\mathrm{principal},\mathrm{action},\mathrm{arguments},\mathrm{result},\mathrm{model},\mathrm{schema\_version},\mathrm{timestamp},\mathrm{provenance}).

model\mathrm{model} holds the model and prompt of the acting agent and is empty for human actors. With a deterministic reducer apply:𝒮owned×Event→𝒮owned\mathrm{apply}:\mathcal S^{\mathrm{owned}}\times\mathrm{Event}\to\mathcal S^{\mathrm{owned}}, the application’s owned persistent state can be reconstructed as

Logt=(e1,…,et),Stowned=fold⁡(apply,S0owned,Logt).\mathrm{Log}_t=(e_1,\ldots,e_t), \qquad S_t^{\mathrm{owned}}=\operatorname{fold}\!\left(\mathrm{apply},S_0^{\mathrm{owned}},\mathrm{Log}_t\right).

Why replay is deterministic. TT is stochastic (§9), but each event records the outcome that TT produced, including model outputs and external responses, in its result\mathrm{result} field. The randomness is resolved once, at execution, and stored. So the fold is deterministic even though execution was not (§20, P1).

Example sequence:

SourceAdded(video_123)
TranscriptExtracted(video_123)
WorkflowDetected(workflow_17)
WorkflowLinked(workflow_17, ext_workflow_4)
SkillGenerated(skill_39)
SkillEvaluated(skill_39, score=.84)
ClaimAdded(claim_88, about=skill_39, source=SkillEvaluated, confidence=…)

The last line follows from §3: an evaluation score is a claim with a source, so it also creates a claim record.

Schema versions. Event formats change over time. Each event carries its schema version, and apply\mathrm{apply} handles every version still in the log, or the log is migrated once.

This is event sourcing. It supports audit trails, time travel, provenance, reproducibility, debugging, and accountability. Reconstruction requires a complete log and stable reducer semantics; external reality or unrecorded ephemeral state cannot be recovered from the application’s events alone. Event sourcing is an architectural option, not a mathematical requirement of the theory.

12. State invariants

An invariant I∈𝒞I\in\mathcal C is a predicate on owned states. The system is safe if I(S)I(S) holds for every I∈𝒞I\in\mathcal C and for every owned state SS reachable from S0ownedS_0^{\mathrm{owned}}. For example:

∀x∈Experiment,x.result≠⌀⇒x.code_version≠⌀,\forall x\in\mathrm{Experiment},\quad x.\mathrm{result}\ne\varnothing\ \Longrightarrow\ x.\mathrm{code\_version}\ne\varnothing,

published(x)⇒human_approved(x).\mathrm{published}(x)\ \Longrightarrow\ \mathrm{human\_approved}(x).

Define

𝒮validowned={S∈𝒮owned:⋀I∈𝒞I(S)}.\mathcal S^{\mathrm{owned}}_{\mathrm{valid}}=\Big\{S\in\mathcal S^{\mathrm{owned}}:\ \bigwedge_{I\in\mathcal C}I(S)\Big\}.

Then constrain the kernel:

Pr⁡(ω(St+1)∈𝒮validowned∣St,it,at)=1.\Pr\!\left(\omega(S_{t+1})\in\mathcal S^{\mathrm{owned}}_{\mathrm{valid}}\mid S_t,i_t,a_t\right)=1.

This form holds for discrete and continuous state spaces. It is a formal specification; its enforcement depends on transactional checks and correct implementations. The commit applies the action to a candidate owned state, checks auth\mathrm{auth} and every I∈𝒞I\in\mathcal C, and on failure appends Rejected(i,a,reason)\mathrm{Rejected}(i,a,\mathrm{reason}) with apply(S,Rejected(…))=S\mathrm{apply}(S,\mathrm{Rejected}(\ldots))=S.

Roles. The policy check (§6) is the primary gate. Invariants restate the highest-risk policy rules as state properties, as published⇒human_approved\mathrm{published}\Rightarrow\mathrm{human\_approved} does. The commit checks them after it applies the action, so a bug in the policy check cannot produce an invalid owned state.

External conditions. The application cannot guarantee that an external system stays valid, so invariants range over owned state only. Conditions on Êt\widehat E_t are monitored conditions: they raise an alert when violated, but they cannot be enforced.

Liveness

Invariants are safety properties: nothing bad happens. Liveness properties say that something good eventually happens, and they are not state predicates. Two are required:

□(pending(p)⇒◇final(p)),□(running(j)⇒◇¬running(j)),\Box\left(\mathrm{pending}(p)\Rightarrow\Diamond\,\mathrm{final}(p)\right), \qquad \Box\left(\mathrm{running}(j)\Rightarrow\Diamond\,\lnot\mathrm{running}(j)\right),

where final(p)\mathrm{final}(p) means proposal pp is committed, rejected, expired, or stale (§14). Both are enforced with deadlines: every proposal and every run has an expires_at\mathrm{expires\_at}, and a service actor in ℐS\mathcal I_S expires it. The deadline turns a liveness property into a rule that code can enforce.

Checking the specification. States, actions, invariants, and liveness properties are the input format of TLA+. A short TLA+ specification of the workflow and proposal states can be model-checked with TLC for both kinds of property.

13. Goals and utility

For actor ii, let ri:𝒮×𝒜→ℝr_i:\mathcal S\times\mathcal A\to\mathbb R be a per-step reward and define the objective over one task:

Ui=𝔼[∑t=0tendβtri(St,it,at)],0<β≤1,U_i=\mathbb E\left[\sum_{t=0}^{t_{\mathrm{end}}}\beta^t\, r_i(S_t,i_t,a_t)\right], \qquad 0<\beta\le1,

where tendt_{\mathrm{end}} is the step at which the goal gg holds or the task is cancelled (§5). Most AI R&D tasks end, so the sum is episodic; β=1\beta=1 means no discount.

Whose objective. An agent’s objective is its principal’s objective restricted to the task, Ui=Uprincipal(i)U_i=U_{\mathrm{principal}(i)} on the task’s states, subject to the hard constraints in PtP_t. Approval (§14) and invariants (§12) catch the gap between this definition and actual behavior.

In practice, preserve multiple objectives:

𝑼=(Uquality,Ucost,Ulatency,Usafety,Uhumaneffort).\mathbf U=(U_{\mathrm{quality}},U_{\mathrm{cost}},U_{\mathrm{latency}},U_{\mathrm{safety}},U_{\mathrm{human\ effort}}).

For a model router and task xx, use two stages. First, remove every model that breaks a hard constraint:

Allowed(x)={m:risk̂(m,x)≤riskmaxand every other hard constraint holds}.\mathrm{Allowed}(x)=\left\{m:\widehat{\mathrm{risk}}(m,x)\le\mathrm{risk}_{\max}\ \text{and every other hard constraint holds}\right\}.

Then choose among the rest:

J(m,x)=qualitŷ(m,x)−λcost̂(m,x)−μlatencŷ(m,x)−ρrisk̂(m,x),m*=arg⁡maxm∈Allowed(x)J(m,x).J(m,x)=\widehat{\mathrm{quality}}(m,x)-\lambda\,\widehat{\mathrm{cost}}(m,x)-\mu\,\widehat{\mathrm{latency}}(m,x)-\rho\,\widehat{\mathrm{risk}}(m,x), \qquad m^*=\arg\max_{m\in\mathrm{Allowed}(x)}J(m,x).

The hats mark estimates. Each estimate is a claim in KtK_t with a source, such as a benchmark or past runs, and a confidence (§3). After each run, the observed quality, cost, and latency are recorded as events and update the estimates, so the router learns from its own log. The weights λ,μ,ρ\lambda,\mu,\rho are the owner’s stated trade-offs, stored in PtP_t as data. When the objectives must stay separate, the router shows the Pareto set and a human chooses; that is a workflow step (§4), not a formula.

14. Human authority

Classify actions by a function of state, actor, and arguments:

class:𝒮owned×𝒜→{free,approval,forbidden}.\mathrm{class}:\mathcal S^{\mathrm{owned}}\times\mathcal A\to\{\mathrm{free},\mathrm{approval},\mathrm{forbidden}\}.

In each state the classes partition the actions:

𝒜=𝒜free(S)∪̇𝒜approval(S)∪̇𝒜forbidden(S).\mathcal A=\mathcal A_{\mathrm{free}}(S)\ \dot\cup\ \mathcal A_{\mathrm{approval}}(S)\ \dot\cup\ \mathcal A_{\mathrm{forbidden}}(S).

A forbidden action is not admissible: auth(S,i,a)=0\mathrm{auth}(S,i,a)=0. An approval-gated action is admissible only through a committed proposal. The class depends on arguments, not only on the action type. For example, class(S,i,send_email(to))=free\mathrm{class}(S,i,\mathrm{send\_email}(to))=\mathrm{free} if the address toto belongs to principal(i)\mathrm{principal}(i), and approval\mathrm{approval} otherwise. The rules that define class\mathrm{class} live in PtP_t. External irreversible actions are approval\mathrm{approval} by default (§7).

Proposals

For an approval-gated action, the agent prepares a proposed change â\hat a and a reviewable predicted transition:

St→âŜt+1,propose→inspect→authorize→commit.S_t\xrightarrow{\hat a}\widehat S_{t+1}, \qquad \mathrm{propose}\to\mathrm{inspect}\to\mathrm{authorize}\to\mathrm{commit}.

Proposals are state: they exist between propose and commit, both the human and the agent can see them, and they can go stale or expire. The theory defines them through an interface and accepts two representations.

Abstract view. A function viewprop:𝒮owned→\mathrm{view}_{\mathrm{prop}}:\mathcal S^{\mathrm{owned}}\to sets of records

p=(id,actor,principal,â,base_version,diff,external_effects,status,expires_at).p=(\mathrm{id},\mathrm{actor},\mathrm{principal},\hat a,\mathrm{base\_version},\mathrm{diff},\mathrm{external\_effects},\mathrm{status},\mathrm{expires\_at}).

The rest of the theory uses only this view.

Status machine. status∈{pending,approved,rejected,expired,stale,committed}\mathrm{status}\in\{\mathrm{pending},\mathrm{approved},\mathrm{rejected},\mathrm{expired},\mathrm{stale},\mathrm{committed}\}. Allowed moves: pending → approved, rejected, expired, or stale; approved → committed, stale, or expired. Rejected, expired, stale, and committed are final.

Axioms. Every representation satisfies:

  • A1. Each proposal binds actor\mathrm{actor}, principal\mathrm{principal}, â\hat a, and base_version\mathrm{base\_version}, and these fields never change.
  • A2. Status changes only through the allowed moves.
  • A3. A commit of â\hat a is allowed only from approved\mathrm{approved}, and only when the current version equals base_version\mathrm{base\_version}. Otherwise the proposal becomes stale\mathrm{stale} and must be proposed again.
  • A4. The human and the agent read the same records (observation parity, §10).
  • A5. Every proposal has a finite expires_at\mathrm{expires\_at}.

Representation E1. A separate component Propt\mathrm{Prop}_t in SownedS^{\mathrm{owned}}; viewprop\mathrm{view}_{\mathrm{prop}} reads it directly.

Representation E2. Each proposal is a run in WtW_t of a fixed WorkflowDef\mathrm{WorkflowDef} “Proposal” (§4), whose state set is the six status values; viewprop\mathrm{view}_{\mathrm{prop}} selects those runs.

Both representations use the same events: Proposed\mathrm{Proposed}, Approved\mathrm{Approved}, Rejected\mathrm{Rejected}, Expired\mathrm{Expired}, Stale\mathrm{Stale}, Committed\mathrm{Committed}. So the event log does not depend on the representation, and by P1 (§20) a system moves from E1 to E2 or back by replaying the same log with a different reducer. P3 (§20) uses only A1–A3, so it holds for both.

Preview. Ŝt+1\widehat S_{t+1} is a prediction, and under the stochastic TT the outcome can differ, especially for external effects. So the preview has two parts. diff\mathrm{diff} is the exact owned-state change, computed by applying â\hat a to a copy of SownedS^{\mathrm{owned}}. external_effects\mathrm{external\_effects} lists the declared external calls, marked “will attempt”. After the commit, the actual external results are recorded next to the declared effects; a mismatch is an event the human can see.

Approval attaches to a concrete action and state version (A1, A3). If that version changes before commit, the system revalidates the proposal.

Reviewer capacity and approval rate

The value of an approval depends on the human’s attention. The theory handles every approval rate α∈[0,∞)\alpha\in[0,\infty) with three parameters:

  • α≥0\alpha\ge0: approvals per unit time;
  • ν≥0\nu\ge0: careful reviews the human can do per unit time (review time available divided by the time of one careful review);
  • ε0∈[0,1]\varepsilon_0\in[0,1]: the probability that a careful review misses a bad proposal.

The share of approvals that received a careful review is

f(α)={1α≤ν,ν/αα>ν.f(\alpha)=\begin{cases}1 & \alpha\le\nu,\\ \nu/\alpha & \alpha>\nu.\end{cases}

Assume the worst case: an approval without a careful review approves any content. Then the probability that the gate lets a bad proposal through is at most

ε(α)=f(α)ε0+(1−f(α))=1−f(α)(1−ε0).\varepsilon(\alpha)=f(\alpha)\,\varepsilon_0+\left(1-f(\alpha)\right)=1-f(\alpha)\left(1-\varepsilon_0\right).

This is an upper bound, not an estimate. For α≤ν\alpha\le\nu, ε(α)=ε0\varepsilon(\alpha)=\varepsilon_0. As α→∞\alpha\to\infty with ν\nu fixed, ε(α)→1\varepsilon(\alpha)\to1: the gate stops bad proposals with probability approaching 00. A human with no review time, ν=0\nu=0, gives ε=1\varepsilon=1 for every α>0\alpha>0. At α=0\alpha=0, no gated action commits; by A5 and the deadlines of §12, every proposal ends as expired, so liveness holds and progress on gated work is 00.

What does not depend on α\alpha. The invariants (§12, P2) and the version binding (A3, P3) hold at every rate (§20, P4). So every rule that must hold at any rate belongs in 𝒞\mathcal C, not in the gate. Only the gate’s filtering value, 1−ε(α)1-\varepsilon(\alpha), depends on α\alpha; this links UhumaneffortU_{\mathrm{human\ effort}} (§13) to safety.

Measured, not assumed. α\alpha is counted from the log: the number of Approved\mathrm{Approved} events in a window divided by the window length. ν\nu and ε0\varepsilon_0 are claims in KtK_t with a source and a confidence. No new state component is needed.

Adaptive policy (optional). class\mathrm{class} may read α\alpha and ν\nu and move action types between free\mathrm{free} and approval\mathrm{approval} as load changes. The theory allows this and does not require it. Recommended default: external irreversible actions stay approval\mathrm{approval} at every rate.

15. Concurrency

Two agents may act on the same state. One solution serializes the actions:

St→(i,a)St+1→(i′,a′)St+2.S_t\xrightarrow{(i,a)}S_{t+1}\xrightarrow{(i',a')}S_{t+2}.

Another merges compatible concurrent updates. Let ee and e′e' be two events that read the same base version of SownedS^{\mathrm{owned}}:

St+1=M(apply(St,e),apply(St,e′)).S_{t+1}=M\!\left(\mathrm{apply}(S_t,e),\ \mathrm{apply}(S_t,e')\right).

MM is a partial function. It is defined when the two updates touch disjoint parts of the state, or when their data type has a join. Otherwise the second commit returns Conflict(version)\mathrm{Conflict}(\mathrm{version}), and the actor re-reads and retries. This is optimistic concurrency. For a conflict in text written by a human and an agent, the system escalates to the human and does not retry automatically.

Some replicated data supports a CRDT-style join ⊔\sqcup with

x⊔y=y⊔x,(x⊔y)⊔z=x⊔(y⊔z),x⊔x=x.x\sqcup y=y\sqcup x, \qquad (x\sqcup y)\sqcup z=x\sqcup(y\sqcup z), \qquad x\sqcup x=x.

These properties, together with the delivery of every update to every replica, yield convergence for the relevant data type. An application with one commit point has delivery at once; CRDTs are needed only for offline or multi-device copies. They do not make arbitrary business operations commute: publication, payments, and uniqueness constraints generally require coordination or transactions.

Which invariants need coordination. An invariant can be kept without coordination if and only if merging any two valid states gives a valid state; this is invariant confluence (Bailis et al., “Coordination Avoidance in Database Systems”, PVLDB 8(3), 2014). Uniqueness fails this test, and so does “balance ≥0\ge0” once withdrawals exist; “append a comment” passes. Apply this test to each invariant in 𝒞\mathcal C.

Agent writes. Every agent write carries the version it read, base_version\mathrm{base\_version} (§10). The commit checks that the data the write depends on has not changed since base_version\mathrm{base\_version}; otherwise it returns Conflict\mathrm{Conflict}. This is the approval-version mechanism of A3, applied to every agent write.

16. Causality and provenance

Let a provenance DAG be

Πt=(Nt,LtΠ),\Pi_t=(N_t,L_t^{\Pi}),

where x→yx\to y means “yy was derived using xx.” For example:

Video→Transcript→Claim→Workflow→Skill→Experiment→Conclusion.\mathrm{Video}\to\mathrm{Transcript}\to\mathrm{Claim}\to\mathrm{Workflow}\to\mathrm{Skill}\to\mathrm{Experiment}\to\mathrm{Conclusion}.

Node types. Following the W3C PROV data model (PROV-DM, W3C Recommendation, 2013), NtN_t has three node types: entities (a transcript, a claim), activities (an extraction run), and agents, which are the Actor\mathrm{Actor} nodes of §2. With activities and agents, the chain above expands to statements such as: claim_88\mathrm{claim\_88} was generated by run_88\mathrm{run\_88}; run_88\mathrm{run\_88} used transcript_123\mathrm{transcript\_123}; run_88\mathrm{run\_88} was associated with Opus5.5\mathrm{Opus5.5}. The source srcn\mathrm{src}_n of a claim (§3) is such a node.

A conclusion yy has an ancestry Anc⁡(y)\operatorname{Anc}(y) that an agent can inspect when asked, “Why do you believe this?” The answer can name the model, the run, and the source, for example “Opus 5.5 extracted it from transcript 123 in run 88”. Provenance records derivation, not truth; the ancestral evidence still needs evaluation.

Immutable versions. Nodes of Πt\Pi_t are immutable versions. A revision creates a new node with an edge “was revision of” to the old version, so Πt\Pi_t is acyclic by construction. In storage, claim and artifact rows are append-only.

Invalidation. When a source is retracted, or a model run is found to be bad, every node in Desc⁡(x)\operatorname{Desc}(x), the descendants of that node xx, is marked suspect. This is the main practical use of the graph.

17. The full formal object

Define an agent-native application as

𝔄=(𝒮,ℐ,{𝒜i},T,{Oi},{ri},S0,apply,𝒞,Meta).\boxed{\mathfrak A=\left(\mathcal S,\mathcal I,\{\mathcal A_i\},T,\{O_i\},\{r_i\},S_0,\mathrm{apply},\mathcal C,\mathrm{Meta}\right)}.

Fixed and changing parts. 𝔄\mathfrak A holds what does not change during operation: types, schemas, the reducer, the fixed invariants, and the rule for changing policy. Invariants that users add at run time are rules in PtP_t, not members of 𝒞\mathcal C. An example of Meta\mathrm{Meta}: only a human changes permissions; an agent may propose a change (§14).

The formalism combines ideas from partially observable decision processes, multi-agent systems, database transition systems, event-sourced architectures, typed knowledge graphs, and authorization logic. It is a design framework assembled from these ideas, rather than a claim that all implementations must use each one. §19 states what makes it specific to agents.

The conceptual shift is from a UI, business logic, and database toward state space, transitions, actors, observations, constraints, and provenance. A GUI, CLI, Codex, Claude Code, API, or background agent is an interface that observes and changes the same modeled system.

Interfaces

An interface is a pair ι=(Oι,𝒜ι)\iota=(O_\iota,\mathcal A_\iota): an observation projection and a subset of actions. A GUI and Claude Code are two interfaces over the same SS and TT. Parity (§19) is a relation between two such pairs.

A further mathematical direction

One can study a category whose objects are valid states and whose morphisms are permitted transitions S→(i,a)S′S\xrightarrow{(i,a)}S'. Workflow sequencing corresponds to composition when transitions are composable. If the morphisms are all finite sequences of permitted transitions, the result is the free (path) category on the transition graph: the identity is the empty path, and composition is concatenation. It always exists, and by itself it adds no theorem. Value would come from functors, for example a map from workflow runs to provenance subgraphs that preserves composition. For stochastic transitions, the standard setting is the Kleisli category of the Giry monad (Giry, 1982), whose morphisms are Markov kernels such as TT. This is a possible formal extension, not a result established by the model above: concurrency, observations, and authorization still need careful treatment before claiming a full categorical theory.

19. What makes an application agent-native

The tuple 𝔄\mathfrak A also describes a multi-user application with a webhook bot. Four properties separate an agent-native application. This revision adopts all four as a default; each is independent, so removing one does not affect the others. Each comes with a test.

  • N1. Action parity. Every action a human can take through the GUI has an agent-callable equivalent that produces the same event type, subject to auth\mathrm{auth}. Test: for each GUI action, a tool call exists that produces the same event.
  • N2. Observation parity. For the part of SownedS^{\mathrm{owned}} that an action depends on, the human and agent interfaces expose the same content (§10). Test: for each action, compare the fields that each interface shows before the action.
  • N3. Self-describing action space. 𝒜i(St)\mathcal A_i(S_t) and the schemas are readable by the agent as observations, and the tool list is generated from policy (§5). Test: the tool list shown to the agent equals the admissible action families computed from PtP_t.
  • N4. Proposals as first-class state. Proposals are readable and actionable from both interfaces (§14, A4). Test: a proposal created in one interface is visible and can be approved or rejected in the other.

A multi-user application with a webhook bot satisfies 𝔄\mathfrak A but in general not N1 and N3.

20. Consequences

Four results follow from the definitions. Each one has a short proof, a condition under which it fails, and a test.

P1. Replay determinism. Let apply\mathrm{apply} be a pure function. If every event records the sampled outcome of its action in result\mathrm{result}, including external responses and model outputs, then StownedS_t^{\mathrm{owned}} is fixed by S0ownedS_0^{\mathrm{owned}} and Logt\mathrm{Log}_t alone. Proof: induction on tt; each step applies a pure function to recorded inputs. Fails if the reducer reads a clock, calls an API, or samples a model during replay. Test: replay the log into an empty database and compare with the live state.

P2. Safety by induction. If S0owned∈𝒮validownedS_0^{\mathrm{owned}}\in\mathcal S^{\mathrm{owned}}_{\mathrm{valid}}, and every commit atomically checks auth\mathrm{auth} and every invariant in 𝒞\mathcal C on the candidate owned state and applies Rejected\mathrm{Rejected} on failure (§12), then every reachable owned state is in 𝒮validowned\mathcal S^{\mathrm{owned}}_{\mathrm{valid}}. Proof: induction on tt; a commit either passes all checks or leaves the state unchanged. Fails for invariants over ErealE^{\mathrm{real}}, which cannot be enforced this way (§12), and if a write bypasses the commit path. Test: a property test that runs random action sequences and checks every invariant after each commit.

P3. Approval soundness. Under axioms A1–A3 (§14), every committed approval-gated action was applied to the exact state version the human approved. Proof: A3 allows a commit only from approved\mathrm{approved} with current version =base_version=\mathrm{base\_version}; A1 fixes base_version\mathrm{base\_version} and â\hat a at proposal time; A2 prevents any other path to committed\mathrm{committed}. Limit: reviewed does not mean understood (§14, reviewer capacity), and external outcomes can still differ from Ŝt+1\widehat S_{t+1}. Test: change the state between approval and commit, and expect stale\mathrm{stale}.

P4. Rate independence. P2 and P3 hold for every approval rate α∈[0,∞)\alpha\in[0,\infty). Proof: neither proof uses α\alpha, ν\nu, or ε0\varepsilon_0. Consequence: only the gate’s filtering value 1−ε(α)1-\varepsilon(\alpha) depends on the rate (§14), so any rule that must hold at every rate goes into 𝒞\mathcal C.
